# Мультиагент против одного агента (ДЗ 6.5)

Код — `experiments/` (`multi_agent_langgraph.py`, `single_agent_baseline.py`, общий `common.py`, оценка
`judge_results.py`), сырые замеры — `experiments/results.json`, схема графа — `docs/architecture-multi-agent.md`.
Модель везде `openai/gpt-5.4-mini` (OpenRouter), 13.10.2026.

## Сценарий

- **Вход:** вопрос пользователя о личных финансах (налоги, вклады, мошенничество).
- **Роли:** researcher собирает факты из базы знаний через `search_knowledge_base` и возвращает их списком с
  источниками; writer по этому списку пишет ответ; supervisor передаёт управление researcher → writer.
  Single-agent делает обе работы сам.
- **Формат ответа:** 2–5 предложений на русском, каждое утверждение со ссылкой [1], [2], в конце — список
  источников; если в базе ответа нет — честный отказ.

Вопросы (одни и те же для обеих реализаций): 3 по корпусу (вычет за лечение зубов, страхование вкладов АСВ,
звонок «службы безопасности банка»), 1 многошаговый (сравнить вычет по ИИС-3 и за обучение, можно ли оба сразу),
1 вне базы (загранпаспорт).

**Честность сравнения.** Tool — один объект `search_knowledge_base` из `experiments/common.py` (RAG из модуля 5,
top-1 фрагмент со score-guard) в обоих скриптах. Токены и число вызовов модели считаются callback'ом на **каждый**
вызов LLM: у supervisor с `output_mode="last_message"` промежуточные шаги researcher в итоговый state не попадают,
и подсчёт по сообщениям занизил бы стоимость мультиагента. Качество — одним судьёй (Gemini 3.8 Flash, как в 5.6):
RAGAS faithfulness по фрагментам, которые вернул tool в этом же прогоне, и `has_citation`.

**Почему `create_supervisor`, а не ручной `Command(goto=…)`.** Для двух агентов с линейным сценарием готовый
supervisor даёт handoff-инструменты и маршрутизацию без своего кода — сравнивается сама идея нескольких агентов,
а не качество нашей маршрутизации. Как оказалось (ниже), именно маршрутизация через LLM и стала слабым местом.

## Сравнение

| Метрика | Single-agent (среднее по 5) | Multi-agent (среднее по 5) | Δ |
|---|---|---|---|
| Токены на запрос | 993 | 2 740 | **× 2,76** |
| LLM-вызовов на запрос | 2,0 | 5,6 | × 2,8 |
| Latency p50, мс | 6 278 | 10 769 | × 1,72 |
| Передач управления на запрос | 0 | 3,6 | +3,6 |
| Качество: RAGAS faithfulness (4 вопроса по базе) | **0,964** | 0,917 | −0,047 |
| Цитаты в ответе (`has_citation`) | 5 / 5 | 5 / 5 | 0 |
| Отказ на вопросе вне базы | верный | верный | — |

По вопросам (`results.json`): на трёх простых качество одинаковое (faithfulness 1,0 у обоих), на многошаговом
мультиагент хуже — 0,667 против 0,857: supervisor завершил работу после researcher'а, не вызвав writer, и
пользователь получил сырой список фактов (`answered_by: researcher`). Single-agent на этом же вопросе за 2 вызова
модели сделал несколько поисков параллельно и сам собрал сравнение.

**Вывод.** Мультиагент не дал прироста качества — на многошаговом вопросе даже потерял, — а стоил в 2,8 раза
больше токенов и вызовов и в 1,7 раза дольше по медиане. Для этой задачи он не оправдан: researcher и writer
работают последовательно над одним и тем же коротким контекстом, параллелить нечего, а каждая передача
управления — лишний вызов модели и лишнее место, где теряется информация.

## Что сломалось по дороге (три прогона)

1. **Supervisor пропускал writer** (`results_v1_supervisor_skips_writer.json`): с промптом «сначала researcher, затем
   writer, сам не отвечай» supervisor в 4 из 5 вопросов получил факты и ответил сам — без writer и без цитат.
2. **Потеря фактов при передаче** (`results_v2_researcher_empty.json`): после ужесточения промпта supervisor звал
   writer, но на двух вопросах writer писал «в базе ответа нет», хотя поиск нашёл нужные документы. Причина:
   промпт researcher «финальный ответ пользователю НЕ пиши» модель местами поняла как «не пиши ничего» —
   последнее сообщение researcher было пустым, а в режиме `last_message` дальше уходит только оно; результаты
   поиска остались внутри researcher. Исправлено промптом: «последнее сообщение ОБЯЗАТЕЛЬНО содержит список
   фактов — только его увидит writer».
3. **Финальный прогон** (`results.json`): writer отвечал в 4 из 5 вопросов, но на многошаговом supervisor снова
   завершил работу без writer. Маршрутизация через LLM не детерминирована даже при явном порядке в промпте.

Оба сбоя — типовые для мультиагентов: неверная маршрутизация и потеря контекста на передаче. У одного агента
этих мест отказа просто нет.

## Сравнение с ориентиром Anthropic

В «How we built our multi-agent research system» (Anthropic, июнь 2025) мультиагентная система тратит
**≈ 15× токенов** обычного чата и даёт **+90,2 %** качества — но на breadth-first research, где субагенты
параллельно исследуют независимые направления, каждый в своём контексте, а результаты сводятся в конце. У нас
множитель токенов — **× 2,76** к single-agent (меньше, потому что агентов два и они не ведут собственных длинных
исследований), а прирост качества — **отрицательный** (−0,047 faithfulness). Наша задача — противоположный случай
из той же статьи: короткий общий контекст, жёстко связанные шаги (писать можно только после поиска), нечего
распараллеливать. Это именно те признаки, при которых, по Anthropic, мультиагент проигрывает одному агенту.

## Решение

**Не использую мультиагент в дипломе.** Agent-слой — один агент с tools: custom `StateGraph` из 6.3/6.4
(`app/services/agent_persistent.py`) с checkpointer и подтверждением перед отправкой письма. Обоснование:

- признаки задачи — общий короткий контекст, последовательные связанные шаги, есть необратимое действие (HIL),
  ответ нужен быстро (бот) — это случаи, где мультиагент проигрывает;
- собственные числа: × 2,8 токенов и вызовов, × 1,7 latency при faithfulness 0,917 против 0,964 и двух новых
  классах сбоев (пропуск writer'а, потеря фактов на передаче).

Если когда-нибудь понадобится разделение ролей «найти → оформить», его надёжнее сделать **фиксированным
workflow** (ребро researcher → writer в графе), а не LLM-supervisor'ом: маршрут известен заранее, и доверять его
модели — значит платить за решение, которое не нужно принимать.
