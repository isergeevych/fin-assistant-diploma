# Оценка качества RAG (ДЗ 5.6)

Все числа скопированы из `tests/eval/results/*.json|csv`. Прогоны от 12–13.10.2026, 37 вопросов, RAGAS 0.4.3.

## 1. Конфигурация

| Компонент | Значение |
|---|---|
| Корпус | `data/`: 56 документов (налоги, вклады и кредиты, бюджет, мошенничество, FAQ приложения, 1 нерелевантный) |
| Эмбеддинги | `qwen3-embedding:0.6b` (Ollama, CPU), 1024 измерения, инструкция для запроса (асимметричная модель) |
| Векторная БД | Qdrant 1.19, косинус, фильтр `status != archived` |
| Чанкинг | `SentenceSplitter` 512 / 64 токена (recursive). Документы короткие → **1 фрагмент на документ** (56 точек) |
| Retrieval | top-10 по вектору → re-ranker `bge-reranker-v2-m3` (CPU) → top-5 в промпт |
| Отказ | двухслойный: код (rerank < 0,1, без re-ranker — вектор < 0,35) + промпт («нет во фрагментах — скажи») |
| Генерация | `openai/gpt-5.4-mini` через OpenRouter, `reasoning_effort: none`, ответ с маркерами [1], [2] |
| Судья RAGAS | `google/gemini-3.8-flash`, `reasoning_effort: low` (выключить reasoning у Gemini нельзя) |
| Эмбеддинги судьи (AnswerRelevancy) | те же `qwen3-embedding:0.6b` |

Отличия от шаблона задания и почему:

- **Судья — Gemini, а не Claude Sonnet.** Бюджет $10 на все облачные прогоны курса: Sonnet ($2/$10 за 1M) дал бы
  ~$2 за прогон. Gemini 3.8 Flash — цена production-модели, но **другой вендор**, чтобы судья не «болел за своих».
  Плюс Sonnet 5.5 в соседнем ДЗ 3.7 отказывал на промпте судьи (`content_filter`). Смена судьи делает числа
  несравнимыми с любыми прошлыми прогонами — все три прогона ниже сделаны одним судьёй.
- **Эмбеддинги судьи локальные**, а не `text-embedding-3-small`: ключа OpenAI нет, а AnswerRelevancy нужно лишь
  сравнить два вопроса между собой — любая приличная модель подходит, главное — одна и та же во всех прогонах.
- **Локальная видеокарта не используется** (с 11.10 сбоит: 4 аварийные перезагрузки под нагрузкой Ollama) —
  генерация и судья в облаке, эмбеддинги и re-ranker на CPU. Отсюда и большие задержки re-ranker (см. §5).

## 2. Golden dataset

- **Генерация:** RAGAS `TestsetGenerator` (LLM `gpt-5.4-mini`) на корпусе без нерелевантного документа →
  40 пар (`tests/eval/golden_dataset_raw.csv`, отдельный коммит без правок). Стоимость генерации $0,25.
- **Ручная вычитка** — `scripts/curate_golden.py`, у каждой записи поле `review_note` с причиной правки:
  - удалено 5: «склейки» несвязанных документов («АСВ + фишинговые сайты», «лимит за спорт + шкала НДФЛ»), дубли;
  - исправлено 23: вопросы на английском и транслите → русский; вопросы-простыни из 3–4 частей → одна тема;
    эталоны обрезаны до вопроса (иначе context_recall штрафует за то, о чём не спрашивали); вопрос «как
    включить 2FA» → «зачем» (инструкции включения в документе нет);
  - **ловушка с архивом:** генератор построил вопрос по архивному тарифу v1 (249 ₽), который RAG фильтрует
    намеренно, — эталон заменён на действующие 299 ₽ / 2990 ₽;
  - опечатка «Финасовая подушка» оставлена специально — проверка устойчивости;
  - добавлено 2 вопроса вне базы (загранпаспорт, прогноз биткоина) — проверка честного отказа.
- **Итог:** 37 пар (`tests/eval/golden_dataset.json`): 14 одношаговых, 21 многошаговый, 2 вне базы.

## 3. Baseline

`2026-10-12_2302_baseline` — конфигурация из §1.

| Срез | faithfulness | answer_relevancy | context_precision | context_recall | has_citation | latency, ср. |
|---|---|---|---|---|---|---|
| все 37 | **0,922** | **0,726** | 0,946 | 0,973 | **1,000** | 6 113 мс |
| 35 вопросов по базе | 0,975 | 0,768 | 1,000 | 1,000 | 1,000 | медиана 5 760 мс |

Цели чекпоинта (faithfulness > 0,7, answer_relevancy > 0,7, has_citation > 0,95) выполнены. Разница между
строками — два вопроса вне базы: система **правильно** отказала, но RAGAS ставит отказу 0 по faithfulness (в
отказе нет утверждений) и 0 по relevancy (метрика штрафует «уклончивые» ответы). Это свойство метрик, а не
дефект — отказы оцениваются отдельно (§7).

## 4. Эксперимент A — чанкинг: SentenceSplitter → SemanticSplitter

Меняется **один** параметр — стратегия нарезки (`--chunk-strategy semantic`, своя коллекция `kb_semantic`);
re-ranker, top-K, модели — как в baseline. Семантическая нарезка дала 112 фрагментов (≈ 2 на документ).

| Вариант | faithfulness | answer_relevancy | context_precision | context_recall | has_citation | latency, ср. |
|---|---|---|---|---|---|---|
| baseline (recursive 512/64) | 0,922 | 0,726 | **0,946** | **0,973** | 1,000 | 6 113 мс |
| semantic | 0,924 | 0,729 | 0,909 | 0,938 | 1,000 | 2 826 мс |
| Δ | +0,002 | +0,003 | **−0,037** | **−0,035** | 0 | — |

Генерация не изменилась (в пределах шума судьи ±0,01), а retrieval стал хуже: документ разрезан на части,
и в top-5 иногда попадает только одна из них (precision 1,0 → 0,961, recall 1,0 → 0,963 на вопросах по базе).
На корпусе из коротких документов (весь документ ≈ 1 чанк 512) семантическая нарезка не может ничего
выиграть — может только разрезать связный текст. Разница в latency — не эффект чанкинга: прогоны шли в разное
время с разной загрузкой CPU (re-ranker), сравнивать её здесь нельзя.

## 5. Эксперимент B — re-ranker: включён vs выключен

Меняется **один** параметр — `--no-rerank` (сразу top-5 по вектору); коллекция та же.

| Вариант | faithfulness | answer_relevancy | context_precision | context_recall | has_citation | latency, ср. |
|---|---|---|---|---|---|---|
| baseline (top-10 → re-ranker → top-5) | 0,922 | 0,726 | 0,946 | 0,973 | 1,000 | 6 113 мс |
| без re-ranker (top-5 по вектору) | 0,930 | 0,723 | 0,938 | 1,000 | 1,000 | **1 587 мс** |
| Δ | +0,008 | −0,003 | −0,008 | +0,027 | 0 | **−4,5 с** |

По средним RAGAS re-ranker **ничего не даёт** — все Δ в пределах шума судьи. Зато на CPU он стоит +4,5 с на
каждый ответ (медиана 5,8 с против 1,5 с). Но средние не видят главного — **какой слой отказал** на вопросах
вне базы:

| Вопрос | top-1 вектор | с re-ranker | без re-ranker |
|---|---|---|---|
| «Как оформить загранпаспорт?» | 0,370 | отказ **кодом** (rerank 0,0002 < 0,1), LLM не вызывается | 0,370 > 0,35 → LLM вызвана, отказала по промпту |
| «Курс биткоина через месяц?» | 0,358 | отказ **кодом** (rerank 0,0003) | 0,358 > 0,35 → LLM вызвана, отказала по промпту |
| для сравнения: «Сколько стоит тариф «Плюс»?» | 0,645 | rerank 0,988 → ответ | ответ |

Без re-ranker защита от «чужих» вопросов держится на одном слое — промпте — и тратит вызов LLM. Это видно и в
Phoenix: в контейнере (там re-ranker выключен ради размера образа) трейс вопроса про биткоин содержит лишний
`ChatCompletion` на 930 токенов — `docs/observability/phoenix_rag_retriever_span.png`.

## 6. Финальная конфигурация

**Беру baseline: recursive 512/64, top-10 → bge-reranker-v2-m3 → top-5, gpt-5.4-mini**, потому что:

- семантическая нарезка хуже по retrieval (precision −0,037, recall −0,035) без выигрыша в генерации;
- без re-ranker средние те же (Δ ≤ 0,03, в пределах шума), но отказ на чужих вопросах переезжает из кода
  в промпт: векторные 0,37 и 0,358 проходят порог 0,35, а re-ranker разделяет их с ответами на порядки
  (0,0002–0,0003 против 0,988, проверено 13.10). Для финансового ассистента надёжный отказ важнее 4 секунд;
- цена re-ranker — 4,5 с на CPU; на GPU это ~0,1 с (§8, план).

Конфигурация — дефолты `app/core/config.py` (`rag_chunk_strategy="recursive"`, `rag_chunk_size=512`,
`rag_chunk_overlap=64`, `rag_retrieval_top_k=10`, `rag_rerank_enabled=True`, `rag_rerank_top_n=5`) и совпадает
с конфигурацией в `2026-10-12_2302_baseline.json`.

| Финал | faithfulness | answer_relevancy | context_precision | context_recall | has_citation | latency, ср. |
|---|---|---|---|---|---|---|
| baseline | 0,922 | 0,726 | 0,946 | 0,973 | 1,000 | 6 113 мс |

## 7. Failure analysis

Пять худших по faithfulness в финальном CSV. Матрица 2×2 из лекции: низкий faithfulness + низкий
context_recall — проблема retriever; низкий faithfulness + высокий context_recall — проблема генерации.

| # | Вопрос | faith | relev | prec | recall | Диагноз |
|---|---|---|---|---|---|---|
| 1 | g37 «Какой курс биткоина будет через месяц?» | 0,00 | 0,00 | 0,00 | 0,00 | **не дефект** — правильный отказ |
| 2 | g36 «Как оформить загранпаспорт?» | 0,00 | 0,00 | 0,00 | 1,00 | **не дефект** — правильный отказ |
| 3 | g20 вопрос-простыня про шкалу НДФЛ | 0,64 | 0,44 | 1,00 | 1,00 | генерация (сжатие) + шум метрики |
| 4 | g02 «Как назначаются категории и как изменить?» | 0,80 | 0,72 | 1,00 | 1,00 | шум судьи |
| 5 | g31 «Лимит 150 000 ₽ и вычеты за спорт и обучение» | 0,80 | 0,77 | 1,00 | 1,00 | генерация: вывод сверх текста + пропуск |

**1–2. Вопросы вне базы.** Retrieved: случайные документы с top-1 0,36–0,37 (финансовые цели, 3-НДФЛ).
Response: «По базе не нашёл ответа, могу передать вопрос специалисту.» — ровно то, что требует эталон.
RAGAS: faithfulness 0 (утверждений нет — делить нечего), relevancy 0 (метрика считает отказ уклончивым),
recall у g36 = 1 (эталон «в базе нет информации» тривиально «покрыт»). Вывод: отказы надо оценивать отдельной
метрикой (доля правильных отказов), а в средние RAGAS не включать — иначе каждый правильный отказ «стоит»
−0,025 к среднему faithfulness на 37 вопросах.

**3. g20** — «Как тут работает зависимость налога от годового дохода… ставка 15% это на весь доход или только
на часть превышения?» (вопрос с опечатками оставлен из генератора). Retrieved: `ndfl_progressive_scale.md`
первым, в нём **все** факты ответа, включая пример с 3 млн ₽ и фразу про работодателя (проверено по тексту
чанка). Response: перечислил ставки «от 2,4 до 5 млн ₽ — 15 %…», а оговорку «с суммы превышения» дал только
вторым предложением. Recall 1,0 + faithfulness 0,64 → по матрице **проблема генерации**: первое утверждение
в сжатом виде неточно (читается как ставка на весь доход), судья справедливо его не засчитал. Relevancy 0,44 —
артефакт метрики: она восстанавливает вопрос из ответа и сравнивает с исходным, а исходный — простыня с
опечатками. Лечение: в промпт — «сохраняй оговорки из источника рядом с числами»; в golden — нормализовать
формулировку.

**4. g02** — Retrieved: `categories.md` первым (precision 1,0). Response: почти дословный пересказ документа с
[1]. Faithfulness 0,8 при дословном ответе — **шум судьи**: одно из 5 утверждений признано неподтверждённым
без видимой причины. Иллюстрирует, почему по одному вопросу ничего не решают: разброс отдельной оценки ±0,2.

**5. g31** — Retrieved: `social_deduction_education.md` и `sport_deduction.md` (оба нужны, оба в top-2).
Response: верно связал лимит 150 000 ₽ со спортом и своим обучением, но (а) добавил вывод «расходы на спорт
и обучение уменьшают один и тот же лимит» — логичный, но в тексте прямо не написанный (судья снял за него
0,2), и (б) не упомянул отдельный лимит 110 000 ₽ на обучение детей, который есть в эталоне. Recall 1,0 →
**генерация**: контекст был, модель им неполно воспользовалась. Лечение: промпт «если вопрос о связи
лимитов — перечисли все лимиты из фрагментов».

Retriever-проблем (низкий recall) в финальной конфигурации нет: на 35 вопросах по базе context_recall = 1,0.
Все потери — в генерации и в свойствах метрик.

## 8. Известные проблемы и план

| Проблема | Почему важно | План |
|---|---|---|
| Re-ranker на CPU: +4,5 с к ответу; в Docker-образе он выключен (torch ≈ +700 МБ при лимите образа) → в контейнере работает только векторный порог 0,35, который пропускает «чужие» вопросы (0,36–0,37) | отказ держится на промпте, лишний вызов LLM | вынести re-ranker в отдельный сервис (свой образ с torch, GPU при наличии) или поднять векторный порог для режима без re-ranker — **после** калибровки на живых, разговорных вопросах (golden «удобный»: минимум в базе 0,626, но вопросы сгенерированы из самих документов) |
| Отказы портят средние RAGAS (0 / 0) | средние faithfulness/relevancy занижены на 0,05/0,04 | отдельная метрика «доля правильных отказов», в RAGAS-средние только вопросы по базе |
| AnswerRelevancy ≈ 0,73 у всех вариантов | впритык к порогу 0,7 | метрика штрафует ответы с дополнительной полезной информацией и вопросы с опечатками; проверить промпт «сначала прямой ответ одной фразой» и отдельно — нормализацию вопросов в golden |
| Шум судьи ±0,01–0,03 на средних, ±0,2 на отдельном вопросе | A/B с Δ < 0,03 не различимы | повторить каждый вариант 3 раза и сравнивать средние с разбросом; для финальной защиты — 50+ вопросов |
| Чанкинг на коротких документах (1 чанк = 1 документ) | эксперимент A мало что может показать | добавить длинные документы (договоры, полные FAQ) и повторить A с chunk_size 256/512/1024 |
| Бот опрашивает `/internal/broadcasts/pending` каждые 15 с — каждый опрос виден в Phoenix как трейс | шум в трейсах | исключить служебные маршруты из инструментирования FastAPI |
| HallucinationEvaluator Phoenix (опционально) не запускался | нет оценки галлюцинаций на живом трафике | запустить на трейсах из `scripts/send_traces.py` после основных ДЗ |

## Трейсинг (Phoenix)

`docker compose up -d` поднимает Phoenix (127.0.0.1:6006); в lifespan сервиса при
`PHOENIX_LLAMAINDEX_TRACING=true` регистрируется `LlamaIndexInstrumentor` на том же tracer provider, что и
OpenAI-инструментор (`app/observability/tracing.py`). `scripts/send_traces.py` отправляет 24 запроса (20 из
retrieval-набора 5.4 + 4 вне базы) — прогнан трижды, 72 трейса.

- `docs/observability/phoenix_rag_traces.png` — список трейсов `POST /rag/query`;
- `docs/observability/phoenix_rag_trace_tree.png` — раскрытое дерево: `VectorIndexRetriever.retrieve` →
  `ServiceEmbedding.get_query_embedding` → `ChatCompletion` (930 токенов, < $0,01);
- `docs/observability/phoenix_rag_retriever_span.png` — retriever-спан: запрос, документы, **score 0,35**,
  метаданные (`source`, `status: active`).

## Как воспроизвести

```powershell
uv sync --extra eval --extra tracing --extra rerank --group dev
.venv\Scripts\python -m scripts.generate_testset --size 40 --workers 4   # сырой golden
.venv\Scripts\python -m scripts.curate_golden                            # вычитка → golden_dataset.json
.venv\Scripts\python -m scripts.run_eval --label baseline
.venv\Scripts\python -m scripts.run_eval --label semantic --chunk-strategy semantic
.venv\Scripts\python -m scripts.run_eval --label no_rerank --no-rerank
```

Стоимость: генерация golden $0,25, один прогон run_eval на 37 вопросах ≈ $0,4.
